# Council proposals (raw PM roadmaps)

Four PM personas proposed v0.1→v2.0 roadmaps; the chair synthesis is in `../ROADMAP.md`. (The 5th PM — demo/storytelling — was still researching when the council closed; its lens is covered by `demos/`.)


## Professor (Curriculum PM) — lens: learning outcomes, module sequencing, scaffolded difficulty, hands-on exercises, and checks-for-understanding (CFU) gates before each release advances.

_I sequenced six releases as a deliberate difficulty ramp where every release is a self-contained teaching unit that ends in (a) a working demo the attendee runs themselves and (b) an artifact they keep, and is gated by an explicit check-for-understanding before the next release unlocks. The cognitive load rises one new concept at a time: v0.1 "the model talks" (single mental model: container + OpenAI-compatible endpoint), v0.5 "the agent has an identity and a secrets boundary" (persona files + the secrets/loopback rule, introduced early so good hygiene is a habit not a retrofit), v1.0 "the agent has a memory it can reason over" (the priority-map/meeting-notes/tasks source-of-truth separation — the repo's stated core lesson), v1.3 "the agent can act in the real world" (skills + gog + Tavily, the highest-friction unit so it gets its own release and the most lab time), v1.6 "the agent is proactive" (crons + 30s heartbeat — the conceptual leap from reply-only to self-initiating, which beginners find hardest, so it follows only after acting is solid), and v2.0 "the agent has judgment and ships" (auto-resolver act/draft/escalate policy, the nemoclaw model swap to prove provider-portability, and a Gilfoyle-hardened container the attendee takes home). The arc is reverse-engineered from the clawchief install order (gog → skills → workspace source-of-truth → crons → validate) so the workshop literally walks the real build path. I front-loaded Gilfoyle's security notes rather than appending them at the end — each release adds exactly the hygiene the new capability demands (env-only keys before tools touch data, allowlists before crons run unattended, container hardening before they ship), which is both better pedagogy and better security. Durations assume a cohort of mixed-skill builders with ~40-50% hands-on lab time per release; the total (~620 min) fits a two-day workshop with the v1.3 tool-integration release intentionally the longest because real-API friction (OAuth, MCP wiring) is where cohorts stall._

### v0.1 — Hello, Agent — the model behind the curtain
- **Goal:** Get every attendee to a running OpenClaw gateway in Docker, talking to a real model over the Nebius Token Factory OpenAI-compatible endpoint, so they own the mental model 'OpenClaw = execution shell, the LLM = intelligence' before any complexity is added.
- **Modules:** M0 Orientation: what a 'chief of staff AI' is and the clawchief end-state demo (show Anton answering, set the destination), M1 The two-box mental model: OpenClaw (gateway/session/routing) vs the model API; why self-hosting the shell matters, M2 Token Factory basics: OpenAI-compatible baseUrl https://api.tokenfactory.nebius.com/v1/, NEBIUS_API_KEY, picking moonshotai/Kimi-K2.6, M3 First run: docker compose up the clawchief image, `openclaw setup`, one live agent turn, CFU-0.1: attendee explains in one sentence which box supplies intelligence vs execution, and runs a turn that returns model output
- **Demo:** Bring up the clawchief:local container with docker compose, point it at Token Factory (Kimi-K2.6), and send one message ('introduce yourself') — the gateway routes it to Nebius and the model replies in the terminal.
- **Security:** Gilfoyle: the key is a bearer credential — it goes in an env var / state volume, NEVER in the repo, a prompt, or a screenshot; confirm the gateway is bound to 127.0.0.1 loopback, not 0.0.0.0; verify .gitignore already covers docker/.env and *client_secret*/*credentials* before anyone types a real key.

### v0.5 — Giving the agent a self — persona, identity, and the secrets boundary
- **Goal:** Teach attendees to shape who the agent is using OpenClaw's editable bootstrap files (SOUL/IDENTITY/USER) and to internalize the secrets-and-isolation boundary now — so identity and good hygiene are designed in, not bolted on later.
- **Modules:** M4 The workspace as the agent's only cwd: bootstrap files OpenClaw injects (SOUL.md persona, IDENTITY.md, USER.md) and how they steer behavior, M5 Authoring a persona: turning 'Anton, chief of staff to Richard Hendricks' into a SOUL file; voice, scope, what it must never claim to have done, M6 Where state actually lives: ~/.openclaw config, session JSONL transcripts, and the secrets boundary (keys in the state volume, not the workspace repo), CFU-0.5: attendee edits SOUL.md, restarts the turn, and demonstrates a measurable change in the agent's voice/scope; locates where their key is stored and confirms it is not in any tracked file
- **Demo:** Attendee writes their own SOUL.md persona, re-runs a turn, and watches the same model adopt a distinct identity and refusal behavior (e.g. won't claim it 'met' someone) — proving persona files, not the model weights, define the character.
- **Security:** Gilfoyle: persona files are world-readable workspace content — no secrets, tokens, or private personal data in SOUL/USER ever; the boundary is keys-in-state-volume, character-in-workspace. Treat session transcripts under ~/.openclaw/agents/<id>/sessions/ as sensitive (they capture conversation history) and keep them out of any backup allowlist.

### v1.0 — A brain it can reason over — the source-of-truth layer
- **Goal:** Teach the repo's stated core lesson: separate prioritization (priority-map), action policy (auto-resolver, intro level), meeting-note ingestion, and live task state (tasks) into distinct editable files, so the agent reasons over structured context instead of vibes.
- **Modules:** M7 Why separation beats one big prompt: priority-map.md (who/what matters, how urgent) as a distinct layer, M8 Live task state: tasks.md as the single canonical task file + tasks-completed.md archive; 'update the source of truth in the same turn you act', M9 Meeting-notes as a live signal source: meeting-notes.md policy + meeting-notes-state.json, turning notes into tasks, M10 First contact with auto-resolver.md (concept only): the idea that a separate file governs act vs draft vs escalate (deepened in v2.0), CFU-1.0: attendee feeds the agent a fake meeting note; it must classify items through their priority-map and append correctly-prioritized entries to tasks.md, archiving nothing it shouldn't
- **Demo:** Drop a sample Pied Piper meeting note into the workspace; the agent reads priority-map + meeting-notes policy, extracts action items, classifies them by urgency, and writes them into tasks.md in one turn — with the completed archive untouched.
- **Security:** Gilfoyle: these files become the agent's authority surface — anyone who can edit priority-map.md or tasks.md can redirect the agent, so treat the workspace dir's file permissions as an access-control boundary. Establish the rule now: tasks.md/priority-map.md are safe to back up; transcripts and any file containing personal contact data are not.

### v1.3 — Hands in the real world — skills + Google Workspace + web search
- **Goal:** Give the agent real-world reach: package capability as Skills (SKILL.md) and wire the two highest-value, highest-friction integrations — gog for Gmail/Calendar and Tavily for web search. This is the densest lab; real-API friction gets the most time.
- **Modules:** M11 Anatomy of a Skill: SKILL.md, the loading-precedence ladder (workspace/skills highest), and `openclaw skills install`, M12 Reading the 4 clawchief skills (executive-assistant, business-development, daily-task-manager, daily-task-prep) as worked examples of skill-held workflow logic, M13 Real tools I: gog CLI for Gmail message-level search and multi-calendar reads (and the EA rules: reply-to-message-id, check all calendars), M14 Real tools II: Tavily web search as an MCP tool wired into the container, M15 Authoring your own Skill: take one recurring task and codify it as a new SKILL.md, CFU-1.3: attendee invokes a skill that does a live gog inbox/calendar read AND a live Tavily search, then writes a result back into tasks.md — proving the skill, tools, and source-of-truth loop all connect
- **Demo:** Run the executive-assistant skill against a real (or fixture) Gmail+Calendar via gog, plus a Tavily web-search lookup for a prospect; the agent triages an inbox item, checks calendars before proposing a time, and logs a follow-up task — a full read-tools-act loop.
- **Security:** Gilfoyle: now the agent touches real accounts — gog runs least-privilege (only the Google scopes you need; OAuth desktop-client JSON stays out of the repo, matched by the *client_secret* gitignore); Tavily and any MCP server get their own scoped API key in the state volume, never the workspace. Gate tool-bearing skills behind config/env so a skill can't silently gain reach. Verify no credential leaked into a SKILL.md or transcript before moving on.

### v1.6 — From reply-only to proactive — crons and the heartbeat
- **Goal:** Cross the hardest conceptual line for beginners: make the agent self-initiating. Teach OpenClaw's in-gateway cron scheduler (at/every/cron), isolated-session jobs, and the 30s heartbeat — turning the assistant from reactive to a true chief of staff that runs sweeps on its own.
- **Modules:** M16 Why proactivity changes everything: time-based events are what make the agent act without being asked, M17 The cron scheduler inside the gateway: jobs.json, the three schedule types (at/every/cron), isolated fresh-context sessions, and the timezone gotcha (cron = host TZ, bare ISO = UTC), M18 The clawchief job set: the recurring EA sweep (*/15 8-21), isolated daily-task-prep and BD sourcing, and why backup/self-update ship DISABLED, M19 The 30s heartbeat (HEARTBEAT.md) and keeping cron prompts short while skills carry the workflow, CFU-1.6: attendee creates one recurring sweep job + one one-shot 'at' job, predicts the next fire time correctly (timezone-aware), and shows the sweep ran in an isolated session and only messaged the principal on real signal
- **Demo:** Enable the executive-assistant sweep cron; let the 30s heartbeat and the scheduled job fire so the agent autonomously runs a triage pass on a fixture inbox and posts a single proactive update to the principal's channel only when there's something actionable — otherwise stays silent.
- **Security:** Gilfoyle: unattended execution is the moment risk spikes. Keep nightly backup and self-update DISABLED until proven; when backup is enabled it must use a deterministic allowlist (stage only restore-critical tracked paths, commit only on non-empty diff) and never stage secrets, transcripts, logs, or media. Confirm cron.enabled scope is intentional and that isolated sessions don't inherit ambient credentials they shouldn't.

### v2.0 — Judgment, portability, and shipping it — the chief of staff goes live
- **Goal:** Graduate the agent: full auto-resolver judgment (act / draft-and-ask / escalate), prove model portability with the nemoclaw swap (OpenClaw on NVIDIA Nemotron via Token Factory), and ship a Gilfoyle-hardened, reproducible container the attendee takes home and runs for real.
- **Modules:** M20 The auto-resolver in full: the four lanes (auto-resolve now / draft and ask / escalate without acting / archive) and the safe-auto-resolve gate (understood + known SoT + operational + clear authority + low-cost-if-wrong), M21 Designing YOUR resolution policy: what your agent may send vs must draft (investor/legal/pricing/press always draft-first) vs must escalate, M22 nemoclaw: swap the model to nvidia/Nemotron via the same OpenAI-compatible endpoint — proving the agent is portable across models, and discussing the throughput/long-context tradeoffs for multi-agent/tool-calling work, M23 Ship it: production hardening, the INSTALL-CHECKLIST validation pass, and the operating-lessons recap as a takeaway runbook, CFU-2.0 (capstone): attendee runs three signals — one the agent auto-resolves, one it correctly drafts-and-asks, one it escalates without acting — passes the INSTALL-CHECKLIST, and demonstrates the same workspace working under both Kimi-K2.6 and Nemotron
- **Demo:** Capstone: feed the live agent a low-risk scheduling email (it auto-resolves and updates tasks.md), an investor reply (it drafts and asks rather than sending), and an ambiguous high-stakes message (it escalates with one crisp summary) — then re-run the exact same workspace on Nemotron (the nemoclaw demo) to show identical behavior on a different model.
- **Security:** Gilfoyle (final hardening): lock the auto-resolve lane to low-risk/reversible only — anything financial, legal, investor, pricing, or public-facing is draft-first by policy, never auto-sent. Ship the container hardened: loopback-bound gateway, secrets only in the state volume, least-privilege tool scopes, key-rotation procedure documented, backup/self-update still off-by-default, and a final 'no secret in repo/transcript/image-layer' audit before the attendee deploys.


## Maya — Pragmatic MVP PM. Lens: fastest path to a working demo, ruthless scope-cutting, every release independently shippable and runnable by an attendee in under 30 minutes.

_I optimized the arc for "working software at every checkpoint" over conceptual completeness. Five releases, each a standalone hands-on lab an attendee finishes in <30 min, each leaving a runnable agent on disk. The spine: get a reply on a real channel (v0.1) -> make it YOUR agent via the workspace source-of-truth files (v0.5) -> give it real-world reach via skills + Tavily/gog (v1.0) -> make it proactive via crons so it acts unprompted (v1.5) -> swap the brain to Nemotron and ship the locked-down "nemoclaw" demo (v2.0). Pied Piper (Richard/Anton/Gilfoyle) is the running narrative so each lab produces a recognizable artifact. Scope cuts I made deliberately: no multi-agent orchestration, no custom channel adapters, no fine-tuning, no production HA — those are conceptually tempting but blow the 30-min budget and aren't load-bearing for the payoff. Gilfoyle's security note rides on EVERY release rather than being a single bolt-on module, because the #1 way a self-hosted agent demo goes wrong is binding the Gateway to 0.0.0.0; I front-load loopback + pairing on day one and escalate hardening (auth token, tool allow/deny, sandbox.mode, security audit, secrets hygiene) as the agent gains reach and autonomy. Two facts I corrected against the workshop priors and wove in: cron lives at ~/.openclaw/cron/jobs.json with {kind} schedules and agentTurn payloads for isolated sessions (and VPS needs explicit tz); and there are six bootstrap files, not just SOUL.md. Durations are sized so the whole workshop is ~4.25h of labs plus breaks — a single day. Versioning: I used v0.1 -> v0.5 -> v1.0 -> v1.5 -> v2.0 so the jump to 1.0 reads as 'it can actually do useful work' and 2.0 reads as 'the headline nemoclaw demo, shippable.'_

### v0.1 — Hello, Agent — first reply on a real channel
- **Goal:** Every attendee stands up a self-hosted OpenClaw Gateway in Docker and gets their agent to reply to them on a real messaging channel within 30 minutes — proving the end-to-end loop (channel -> Gateway -> Nebius model -> reply) works on their own machine before any customization.
- **Modules:** OpenClaw mental model: the Gateway as control-plane (hub-and-spoke, one agent process per Gateway) and why the LLM is the brain but OpenClaw is the execution environment, Run it in Docker: `openclaw setup` to scaffold `~/.openclaw/openclaw.json` + the workspace, then start the Gateway, Wire the model: point OpenClaw at Nebius Token Factory (OpenAI-compatible baseUrl https://api.tokenfactory.nebius.com/v1/, NEBIUS_API_KEY) using moonshotai/Kimi-K2.6 as the default brain, Connect ONE channel (Telegram or Discord — pick the lowest-friction) and pair your account, The loopback rule: the Gateway binds 127.0.0.1:18789 by default and the Control UI rides the same port — never expose it
- **Demo:** Attendee opens Telegram/Discord, messages their freshly-booted agent 'who are you?', and gets a model-generated reply routed through their local Gateway. The Pied Piper framing: this empty agent is the blank slate that will become 'Anton', Richard's chief of staff. Tear-down/restart proves it survives a Gateway bounce.
- **Security:** Gilfoyle's rule #1: bind the Gateway to loopback (`gateway.bind: loopback`) and NEVER 0.0.0.0 on an untrusted network — that single mistake hands an attacker every agent, credential, and session. Set `dmPolicy: pairing` (default) so only paired accounts can talk to the agent; never `open`. Put NEBIUS_API_KEY in an env var / .env, not in committed config. Run the container as a non-root user. If you must reach it remotely, use SSH tunneling or a private VPN/Tailscale — not a public bind.

### v0.5 — Give it a soul — the workspace as source of truth
- **Goal:** Turn the generic agent into a specific, opinionated assistant by editing the workspace bootstrap files and the workshop's source-of-truth docs — so identity, tone, and operating rules come from version-controllable files the attendee owns, not from prompts typed at runtime.
- **Modules:** The workspace is the agent's only cwd: how OpenClaw injects bootstrap files into the system prompt on first turn, The six bootstrap files and what each is for: IDENTITY.md (name/emoji), SOUL.md (persona/boundaries/tone), AGENTS.md (operating instructions/memory), TOOLS.md (tool guidance), USER.md (user profile), BOOTSTRAP.md (first-run ritual, auto-deletes after it runs), Workshop source-of-truth docs: author priority-map.md, auto-resolver.md, and tasks.md as the agent's working memory of what matters and how to triage, Where memory lives: session transcripts persist as JSONL under `~/.openclaw/agents/<agentId>/sessions/` — and why blank/oversized bootstrap files are skipped or trimmed, Iterate fast: edit a file, start a fresh session, watch behavior change
- **Demo:** Attendee writes SOUL.md + IDENTITY.md to become 'Anton, AI chief of staff to Richard Hendricks' (dry, concise, protective of Richard's focus), seeds priority-map.md with Pied Piper priorities (ship the compression demo; keep Richard out of meetings) and tasks.md with three tasks, then asks 'what should Richard focus on today?' — the agent answers in-character, grounded in the files. Edit priority-map.md, re-ask, and watch the answer move.
- **Security:** Treat the workspace like source code: it now encodes behavior, so put it under git and review diffs — a bad edit to AGENTS.md/SOUL.md is a behavior change. Keep secrets OUT of bootstrap and source-of-truth files (they're injected into prompts and may be echoed); reference env vars instead. Set the `~/.openclaw` state directory to 700 so other local users can't read session JSONL or workspace memory. Back up `~/.openclaw` (state + workspace) before each lab so a broken edit is a 10-second restore.

### v1.0 — Hands and senses — skills that touch the real world
- **Goal:** Give the agent real capability by installing and authoring skills, so it can search the live web (Tavily) and act in Google Workspace (gog CLI) — moving from 'chatbot that knows things' to 'assistant that does things', with an explicit tool-permission boundary.
- **Modules:** Skills = modular capability blocks defined by a SKILL.md (name + description frontmatter, optional `metadata.openclaw` for deps/gating), Loading precedence (highest->lowest): `<workspace>/skills` -> `<workspace>/.agents/skills` -> `~/.agents/skills` -> managed `~/.openclaw/skills` -> bundled; install with `openclaw skills install <slug>` (workspace) or `--global` (shared), Add web research: install/configure a Tavily search skill so the agent can pull current information via the Tavily API/MCP, Add real actions: wire the gog CLI so the agent can read/draft Gmail and read Calendar for Richard, Author your own: write a minimal custom SKILL.md that wraps a shell command, and gate it with `requires.env` / `requires.bins` so it only loads when prerequisites exist
- **Demo:** Anton handles a real request end-to-end: attendee asks 'What's the latest on our top competitor, and draft Richard a 3-line summary email.' The agent uses the Tavily skill to search live, synthesizes, and uses gog to create a Gmail draft addressed from Richard — attendee opens Gmail and sees the draft. Bonus: a custom skill that appends an item to tasks.md so capability and memory connect.
- **Security:** Capability is now attack surface, so Gilfoyle locks the tool boundary: maintain an explicit `tools.allow` allowlist and remember deny rules override allow — grant only the tools this agent needs. Deny dangerous primitives (`exec`, `apply_patch`) by default and only enable per-agent when justified. Treat ClawHub/community skills like untrusted packages — read the SKILL.md and any `metadata.openclaw` install hooks before installing. Scope gog/Google OAuth to least privilege (draft/read, not send-as/admin) and store Tavily + Google tokens as env vars, never in skill files. Watch for prompt-injection: web content the agent reads can carry instructions — keep write/send actions human-in-the-loop (drafts, not auto-sends) at this stage.

### v1.5 — It acts on its own — proactive crons
- **Goal:** Make the agent proactive instead of reply-only by scheduling jobs in the Gateway's cron scheduler, so it runs work on a clock in fresh isolated sessions — the step that turns 'assistant you message' into 'chief of staff that messages you first'.
- **Modules:** The cron scheduler runs inside the Gateway and reads `~/.openclaw/cron/jobs.json` on startup; nothing runs unless `cron.enabled: true`, Three schedule kinds: `at` (one-shot ISO timestamp), `every` (interval in ms), `cron` (5-field expression like `0 7 * * 1-5`), Isolated vs main session: isolated jobs get fresh context and use `agentTurn` payloads (recommended); main-session jobs carry history and use `systemEvent` payloads, Timezone gotcha: cron uses the Gateway host's local tz, so on a UTC VPS you MUST set explicit `"tz": "America/Los_Angeles"`; bare ISO timestamps are treated as UTC, Compose with v1.0: a scheduled job that calls the Tavily + gog skills and reads priority-map.md/tasks.md to produce real output
- **Demo:** Attendee creates Anton's 'Morning Briefing' job — natural-language: 'every weekday at 7am Pacific, check tasks.md and the calendar, search for any overnight news on our competitors, and DM Richard a 5-line briefing.' To prove it without waiting, they also add an `at` job firing 2 minutes out (or trigger a run now), and the briefing lands in their channel unprompted. The proactive loop is visible: no human message triggered it.
- **Security:** Proactive + autonomous raises the stakes, so harden accordingly: jobs run with the agent's full tool grants on a timer with NO human in the loop, so keep autonomous jobs to read/draft/notify actions and require confirmation for anything that sends or mutates external state. Pin `"tz"` explicitly so a job doesn't fire at the wrong hour and spam Richard (an availability/trust failure). Keep isolated sessions (`agentTurn`) the default so a scheduled run can't inherit and leak prior conversation context. Re-run `openclaw security audit` after editing jobs.json, and log job executions so a misbehaving cron is visible. Confirm the Gateway is still loopback-bound — a proactive agent reaching out is fine; an exposed Gateway running crons is a standing breach.

### v2.0 — The nemoclaw demo — swap the brain, lock the box, ship it
- **Goal:** Deliver the headline payoff: re-point the now fully-capable agent from Kimi to NVIDIA Nemotron 3 Super (the 'nemoclaw' demo), validate tool-calling + long-horizon planning on the open model, and package the whole thing as a hardened, reproducible Docker deployment an attendee can hand to a teammate.
- **Modules:** Swap the brain with one config change: set the model to `nvidia/nemotron-3-super-120b-a12b` on the same Nebius baseUrl/key — same Gateway, same skills, same crons, new intelligence, Why Nemotron for agents: 120B/12B-active hybrid Transformer-Mamba MoE, up to ~1M-token context, built for tool calling, multi-step tool use, and long-horizon planning — exercise it against the v1.0 skills, A/B the brains: run the same briefing/research task on Kimi-K2.6 vs Nemotron and compare tool-call reliability, plan quality, latency/throughput, Package for handoff: a single docker-compose + a checked-in workspace + jobs.json so 'clone, set keys, up' reproduces Anton on a fresh machine, Gilfoyle's go-live checklist: the full hardening pass before this leaves your laptop
- **Demo:** The capstone: attendee flips the model to Nemotron and gives Anton a multi-step instruction — 'research our top 2 competitors, draft Richard a briefing email, and add the three biggest threats to tasks.md.' Nemotron plans, chains Tavily + gog + the tasks.md skill in sequence, and completes all three. Then they run `docker compose down && up` and the entire hardened 'nemoclaw' agent — identity, skills, morning cron — comes back. Side-by-side Kimi-vs-Nemotron run shown on screen.
- **Security:** This is the ship gate, so Gilfoyle's full checklist must pass before handoff: Gateway loopback-bound (or behind SSH tunnel / identity-aware VPN — never public 0.0.0.0); strong `gateway.auth.token` set and rotated for any non-loopback bind; `dmPolicy: pairing` not open; explicit `tools.allow` with `exec`/`apply_patch` denied by default; `sandbox.mode: non-main` (or `all`) so tool calls run containerized; container runs non-root with state dir 700; ALL secrets (NEBIUS_API_KEY, Tavily, Google tokens) injected as env/secrets and excluded from the committed bundle via .gitignore; `openclaw security audit` run and saved green; daily backup of `~/.openclaw`. Hand a teammate the repo, not the keys.


## Gilfoyle — Security Ops & IT Infrastructure PM. My lens is non-negotiable: never plaintext keys, least-privilege everything, audit trails on every privileged action, harden the container before you ship it, and treat every third-party skill as hostile until proven otherwise. This roadmap teaches OpenClaw the way it should actually be run in production — secure by default at v0.1, not bolted on at v2.0. Each release ratchets the security posture up one notch while still being a fun, demoable workshop. Worked example throughout: "Pied Piper" (principal Richard Hendricks, AI chief of staff "Anton"), so attendees build one coherent agent across all six releases instead of six throwaway toys.

_The arc moves outward in concentric trust rings, and that ordering is itself the security curriculum. v0.1 stands the Gateway up on loopback with secrets already in env/keychain — we never teach a plaintext-key habit we'd later have to untrain. v0.5 adds capability (Skills) but pairs every new power with its containment (sandboxing tiers, dangerous-code scanner, allowlists) so attendees viscerally learn that the 2026 ClawHub malware incident is the default threat model. v0.8 makes the agent proactive (Workspace source-of-truth files + Crons) and confronts the fact that autonomous cron sessions are an unattended-privilege problem. v1.0 is the first reach OUTSIDE the box — Nebius Token Factory for inference, gog OAuth for Google Workspace, Tavily for search — so it is exactly where least-privilege OAuth scopes, per-skill secret injection, and egress discipline have to land. v1.5 is the hardening release: non-root containers, the three sandbox tiers in anger, `openclaw security audit`, and a real audit/logging pipeline over the JSONL session transcripts. v2.0 ties the ribbon: a multi-agent "Pied Piper" deployment (the nemoclaw demo runs Anton on Nemotron 3 Super) with full key-rotation runbooks, SBOM/supply-chain gating, and an incident-response drill — a production system an auditor would sign off on. Biased toward my lens, but the security work is always in service of a capability the attendee just unlocked, so the whole thing stays teachable and the difficulty curve is honest._

### v0.1 — Loopback & Secrets Hygiene — stand it up without leaking it
- **Goal:** Get a single OpenClaw Gateway running locally for the 'Pied Piper' agent (Anton) bound to loopback, with every credential already living outside the repo and outside the config file. Establish the muscle memory that a plaintext key is a bug, from line one.
- **Modules:** OpenClaw mental model: Gateway as the single control-plane process (hub-and-spoke), channels decoupled from the agent brain, one agent per Gateway, `openclaw setup` — what it writes: config at ~/.openclaw/openclaw.json and the workspace at ~/.openclaw/workspace, The default security posture you inherit: gateway.bind=loopback on 127.0.0.1:18789 + a randomly generated auth token — and why that default exists, Secrets 101: env vars and OS keychain vs. hardcoding; why config files and shell history are the two classic leak paths, Filesystem least-privilege: chmod 700 on ~/.openclaw so the state dir (which will accumulate credentials) isn't world-readable
- **Demo:** Run `openclaw setup`, boot the Gateway, and have Anton answer a first message in one channel (Telegram or Discord) — proving the agent is alive while bound only to localhost. Then deliberately curl the gateway from a second machine / different interface and watch the connection refused, making the loopback boundary concrete.
- **Security:** This is the whole point of the release, so it is the curriculum, not a footnote. (1) Confirm loopback bind — never 0.0.0.0 on an untrusted network; that misconfig is the single most dangerous one. (2) NEVER plaintext keys: keys go in env/keychain, config holds only references; add a pre-commit gitleaks/trufflehog scan so a key can't be committed even by accident. (3) chmod 700 ~/.openclaw. (4) Treat the auth token as a real secret from day one — note that it must be rotated later when we expose anything.

### v0.5 — Skills & the Sandbox — every new power gets a leash
- **Goal:** Give Anton its first real capabilities via Skills, and in the same breath teach that third-party skills are untrusted code. Attendees install a skill AND scope/sandbox it, internalizing capability-with-containment as one inseparable step.
