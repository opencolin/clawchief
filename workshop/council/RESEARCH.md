# Council research (Tavily-grounded facts)

- **OpenClaw — what it is** — OpenClaw is a self-hosted, open-source 'operating system for AI agents' that acts as an abstraction layer between LLMs and the messaging apps you already use (WhatsApp, Telegram, Discord, Slack, Signal, iMessage, Teams). It runs on your own infrastructure (laptop, VPS, Mac Mini, or a cloud/Docker container) and provides session management, memory, tool sandboxing, access control, and message routing around the model — the LLM supplies intelligence, OpenClaw supplies the execution environment.  
  _source: https://ppaolo.substack.com/p/openclaw-system-architecture-overview ; https://codewithyoha.com/blogs/build-cross-platform-ai-agents-with-openclaw-whatsapp-telegram-discord_
- **OpenClaw — Gateway** — The Gateway is the central control-plane process (hub-and-spoke architecture): one agent process per Gateway. CLI tools, web UIs and scripts connect to it as 'clients'; mobile/background agents connect as 'nodes'. All traffic flows through a single port, by default 127.0.0.1:18789 (loopback bind), including the Control UI and routing logic. Channels are decoupled from the agent 'brain', so a channel can fail without taking down the agent.  
  _source: https://nebius.com/blog/posts/openclaw-security ; https://www.linkedin.com/posts/vinothgovindarajan_openclaw-architecture-part-1-control-plane-activity-7429509957747675137-yLVJ_
- **OpenClaw — Skills** — Skills are modular capability blocks (custom scripts / APIs / third-party integrations, each defined by a SKILL.md). OpenClaw loads them by precedence: workspace `<workspace>/skills` (highest), `<workspace>/.agents/skills`, `~/.agents/skills`, managed/local `~/.openclaw/skills`, then bundled skills shipped with the install, plus extra dirs via `skills.load.extraDirs`. `openclaw skills install <slug>` installs into the active workspace's skills/ by default (`--global` targets the shared managed dir); skills can be gated by config/env.  
  _source: https://docs.openclaw.ai/concepts/agent ; https://docs.openclaw.ai/tools/skills_
- **OpenClaw — Crons** — OpenClaw's cron scheduler runs inside the Gateway process and reads jobs.json on startup. Three schedule types: `at` (one-shot), `every` (interval), and `cron` (standard expressions, e.g. `0 9 * * *`). Jobs are defined in natural language and run in isolated sessions (fresh context) by default; cron uses the Gateway host's local timezone while bare ISO timestamps are treated as UTC. If `cron.enabled` is false/missing the scheduler never starts — these time-based events are what make the agent proactive rather than reply-only.  
  _source: https://www.stack-junkie.com/blog/openclaw-cron-jobs-automation-guide ; https://www.meta-intelligence.tech/en/insight-openclaw-cron_
- **OpenClaw — Workspace as source of truth** — OpenClaw uses a single required workspace directory (`agents.defaults.workspace`, default `~/.openclaw/workspace`) as the agent's only working directory (cwd) for tools and context. Inside it OpenClaw injects user-editable 'bootstrap files' (e.g. a SOUL.md persona file) that define identity and behavior; session transcripts persist as JSONL under `~/.openclaw/agents/<agentId>/sessions/`. `openclaw setup` initializes the config (`~/.openclaw/openclaw.json`) and workspace files. (Workshop's priority-map.md / auto-resolver.md / tasks.md are examples of these editable workspace source-of-truth files.)  
  _source: https://docs.openclaw.ai/concepts/agent ; https://generect.com/blog/openclaw-ai-agent_
- **Nebius Token Factory — OpenAI-compatible API** — Nebius Token Factory is Nebius's production-grade managed inference (and fine-tuning) platform exposing an OpenAI-compatible API — you point the OpenAI SDK at base_url https://api.tokenfactory.nebius.com/v1/ with a NEBIUS_API_KEY. It provides autoscaling inference endpoints and dedicated model endpoints with guaranteed performance isolation/SLAs, so teams run open models in production without managing their own vLLM/Ray/Kubernetes GPU serving stack. SDKs/integrations documented include OpenAI-compatible, LiteLLM, ai-suite, and LlamaIndex.  
  _source: https://docs.tokenfactory.nebius.com/api-reference/introduction ; https://github.com/nebius/token-factory-cookbook ; https://strandsagents.com/docs/community/model-providers/nebius-token-factory_
- **Nebius Token Factory — model lineup** — Token Factory hosts a broad open-model catalog. Featured/listed models include DeepSeek (V3.2, V4 Pro), GLM-5.1, Qwen3.5-397B-A17B and Qwen3 variants, moonshotai/Kimi-K2.5 and Kimi-K2.6 (256K context), MiniMax-M2.5, NousResearch Hermes-4 (70B/405B), Meta Llama-3.1/3.3, Google Gemma, OpenAI gpt-oss-120b, and the NVIDIA Nemotron family (incl. Nemotron-3-Super-120B). Nebius is co-developing optimized serving of these open models (DeepSeek, GLM, GPT-OSS, Kimi, Llama, MiniMax, Qwen) with partner Eigen AI.  
  _source: https://mastra.ai/models/providers/nebius ; https://openrouter.ai/provider/nebius ; https://nebius.com/blog/posts/nebius-and-eigen-ai-partner-to-accelerate-frontier-open-source-ai-inference_
- **Nebius — NVIDIA Nemotron 3 Super (the 'nemoclaw' model)** — NVIDIA Nemotron 3 Super is available on Nebius Token Factory: a 120B-parameter open hybrid MoE model that activates only ~12B parameters per inference step (so compute cost ~ a 12B dense model) with up to a 1M-token context window. It uses a hybrid Transformer–Mamba ('LatentMoE', Mamba-2 + MoE + attention) architecture with Multi-Token Prediction, built for multi-agent applications, tool calling, long-horizon planning, and high-accuracy instruction following, delivering ~50% higher token-generation throughput vs leading open models. Fully open (weights/data/recipes).  
  _source: https://nebius.com/blog/posts/nemotron3-super-now-available ; https://www.together.ai/models/nvidia-nemotron-3-super ; https://deepinfra.com/blog/nvidia-nemotron-3-super-deepinfra_
- **Nebius — Kimi K2.6 on Token Factory** — moonshotai/Kimi-K2.6 is offered via Nebius Token Factory (also surfaced through OpenRouter's Nebius provider). It's Moonshot AI's next-gen multimodal model for long-horizon coding, coding-driven UI/UX generation, and multi-agent orchestration, with a 262K-token context window and an 'agent swarm' architecture that scales to hundreds of parallel sub-agents; OpenRouter lists Nebius pricing around $0.95/M input and $4/M output tokens.  
  _source: https://openrouter.ai/provider/nebius_
- **Tavily — what it is** — Tavily is a web-search/retrieval API purpose-built for LLMs and AI agents (and RAG workflows), delivering real-time, ranked, LLM-optimized results rather than a raw SERP. Beyond Search it offers Extract (turn a URL into clean LLM-ready markdown/text), Crawl (navigate whole domains respecting robots.txt), Map, and Research. Official SDKs exist for Python and TypeScript/JavaScript.  
  _source: https://composio.dev/content/tavily-api-ai-agents-introduction ; https://github.com/tavily-ai_
- **Tavily — MCP server for agents** — Tavily ships a production-ready, open-source MCP server (tavily-mcp, ~2k GitHub stars, MIT) exposing real-time search, extract, map & crawl as tool calls so agents (Claude, ChatGPT, goose, OpenClaw, etc.) can call them directly. It installs via `npx -y tavily-mcp` with a TAVILY_API_KEY environment variable; in this workshop the Tavily MCP tools (tavily_search / tavily_extract / tavily_crawl / tavily_map / tavily_research) are the web-search layer.  
  _source: https://github.com/tavily-ai ; https://goose-docs.ai/docs/mcp/tavily-mcp_
- **Tavily — search response shape / controls** — A Tavily search returns URL, title, snippet and a relevance score per result; optional toggles add include_answer (LLM-generated summary), include_raw_content (full page text in markdown/plain), and include_images. It supports search_depth tuning (basic / advanced / fast / ultra-fast), date filtering (start_date/end_date, time_range), domain include/exclude lists, country boosting, and a news topic — typical latency ~2–3s per call.  
  _source: https://parallel.ai/articles/tavily-vs-parallel-search ; https://apify.com/clearpath/tavily-search-mcp_
- **gog (gogcli) — what it is** — gogcli (the `gog` binary) is a single Go-based, script-friendly Google CLI hosted under the openclaw GitHub org (github.com/openclaw/gogcli; site gogcli.sh). One binary covers Gmail, Calendar, Drive, Docs, Sheets, Slides, Forms, Meet, Apps Script, Analytics, Search Console, Contacts, People, Tasks, Classroom, Chat, YouTube, Groups, Keep, and Workspace admin — explicitly built for terminals, shell scripts, CI, and coding agents.  
  _source: https://github.com/openclaw/gogcli ; https://gogcli.sh_
- **gog — install & auth** — Install via Homebrew (`brew install openclaw/tap/gogcli`), Docker, prebuilt Windows ZIPs, or source (needs the Go version in go.mod). First-time setup creates a Google Cloud project, enables the needed APIs, and registers a Desktop OAuth 2.0 client JSON: `gog auth add <email> <client_secret.json>`, then `gog auth list`. It supports multiple Google accounts and OAuth client projects in one config, plus OAuth, direct access tokens, ADC, and Workspace service accounts (domain-wide delegation); containers should use a persistent config volume + encrypted file keyring.  
  _source: https://github.com/openclaw/gogcli ; https://termo.ai/skills/gogcli ; https://gogcli.sh_
- **gog — automation & agent-safety features** — gog is designed for agents/CI: `--json` emits a stable JSON envelope and `--plain` emits TSV on stdout, while all prompts, progress and warnings go to stderr so pipes stay parseable. Account selection is via per-command `--account` or a global GOG_ACCOUNT env var. Safety controls include runtime allow/deny lists (`--enable-commands` / `--disable-commands`), `--gmail-no-send` / `gog config no-send`, `--dry-run`, `--wrap-untrusted`/`--sanitize-content`, read-only audits (Drive tree/du/inventory, Contacts dedupe preview), and baked safety-profile binaries that cannot be reconfigured at runtime.  
  _source: https://gogcli.sh ; https://github.com/openclaw/gogcli ; https://skills.rest/skill/gogcli_
